SYSTEM SPECIFICATION & ARCHITECTURE
Data Warehouse Solution for Online Furniture Retailer
(Online Möbelhandel)
End-to-End Implementation of an Operational Business DB, Dimensional Star Schema, and ETL Pipeline

1. MOTIVATION & BACKGROUND

A German online furniture retailer (comparable to home24) sells furniture and home accessories to private customers throughout Germany. The operational shop database is designed exclusively for processing individual transactional orders answering "what is in order 41725?" quickly. However, it cannot efficiently answer high-level analytical queries such as "how did revenue per product category develop over the last two years?" without executing expensive joins and aggregations across the live database.

This project builds a compact yet complete data warehouse solution for the retailer: a normalized operational source database, a dimensional target model, and a Python-based ETL process connecting the two systems.

2. PROJECT OBJECTIVES

1. Operational Source (Business DB)

Design and implement a relational database in 3NF representing the shop's order-taking process.

2. Target Data Warehouse

Design a Star Schema dimensional model and implement an automated ETL pipeline in Python to transform and load transactional data.

3. Slowly Changing Dimensions (SCD)

Analyze dimension attribute behavior and demonstrate precise handling of SCD Types 0, 1, and 2.

4. Business Intelligence & Analytics

Formulate and execute analytical SQL queries against the warehouse to deliver key operational insights.

3. BUSINESS DB DESIGN

3.1 ERM DESIGN

  • The primary domain covers the order-taking process: a customer (entity Customer) places an order (entity OrderHeader) containing one or more order lines (entity OrderLine).
  • Each order line is associated with the sale of a specific product (entity Product) in a certain quantity. Each product might be discounted for a specific order (e.g., due to a promotional campaign).
  • Each product is assigned to a category (e.g., Sofa, Tisch etc.). A category might be associated with a parent category (e.g., Sofa is associated with the parent category Wohnzimmer).
  • Each product is supplied by a specific supplier (entity Supplier).

3.4 SYNTHETIC DATA GENERATION

  • Real data for a suitable business DB was not available from real sources. Business data was generated synthetically.
  • The python faker module was used for generating realistic customer names and addresses. Because faker generates PLZ and cities independently, faker generated PLZ/city associations are not correct. Therefore, a separate script was used to generate correct PLZ/city associations for 75 cities (city list suggested by AI). This was necessary because analytical questions can be modelled on PLZ/City association.
  • Faker generated street names do match cities - but it is not important because no street level analytics are considered.
  • Product, category and supplier name tables were generated using AI suggestions.

6. ETL PROCESS & TRANSFORMATION LOGIC

6.1 BRIEF CODE OVERVIEW

  • Implemented using python 3.11+, and SQLite3
  • The code is organized in two directories - sql/ and python/
  • sql/ contains all SQL scripts for creating and transforming tables in the data warehouse. These scripts are executed from python code during the data generation and etl process.
    • The scripts for RAW_ to FULL_ table transformations are included in sql/transform/.
    • The scripts for analytics questions are included in sql/analytics/.
  • python/ contains Python scripts for orchestrating the ETL process.
    • python/data_gen/ contains scripts to generate and import business data
    • python/etl/ contains scripts to orchestrate the ETL process (See details below)
    • python/run.py is a menu driven orchestrator script. The script offers menu choices to generate the business DB, run the ETL process, and execute analytics queries. Additionally, it provides an option to generate new order and customer data so as to test the SCD implementation.

6.2 ETL PROCESS

Figure 4 - ETL Process
  • run_all_etl (entire data pipeline)
    • Stage 1: run_etl_extract() Copies business DB to RAW_ tables in the data warehouse
      • apply_dwh_ddl Creates RAW_, FULL_, DIM_, FACT_ tables if they do not exist (sql/02_create_dwh.sql)
      • extract_to_raw
        • Iterates over _RAW_MAP (Business DB to RAW_ table name mapping, e.g. Customer → RAW_BusinessDB_Customer)
        • For each RAW_ table, deletes data and copies from the corresponding Business DB table.
    • Stage 2: run_etl_transform() → Transforms RAW_ tables into FULL_ tables
      • Executes the 3 transformation scripts for the 3 FULL_ tables (from sql/transform/)
      • Each script performs the following: Deletes existing table data and copies data from RAW_ tables while transforming it.
        • For customers → Additional PlzZone and PlzRegion are added
        • For products → Category name and top category names are added by joining with the Category table (flattening of category hierarchy)
        • For sales → Full sales table is created by joining order header, order line, and product data (i.e. each line corresponds to an order line)
    • Stage 3: Update dimension and fact tables
      • run_etl_dim_date()
        • DIM_Date stores all unique order dates with a surrogate key in the form <<YYYYMMDD>>, i.e. by replacing the - in the original date with an empty string.
      • run_etl_dim_supplier()
        • Inserts new supplier IDs with a surrogate key into DIM_Supplier if new suppliers are added to the business DB.
      • run_etl_dim_product()
        • Inserts a new product ID with a surrogate key into DIM_Product if new products are added to the business DB.
        • If any attribute of a product is updated in the business DB, the corresponding record in DIM_Product is also updated (SCD 1 approach).
      • run_etl_dim_customer()
        • Inserts a new customer ID with a surrogate key into DIM_Customer if new customers are added to the business DB.
        • If the address of a customer is changed, the corresponding record in DIM_Customer is updated by changing IsCurrent to 0 and inserting a new record with the updated address (IsCurrent = 1) (SCD 2 approach). See the SCD logic table below for details.
      • run_etl_fact_sales()
        • Inserts new sales records into FACT_Sales if new sales are added to the business DB.
        • For customers, the current surrogate key from DIM_Customer is used to maintain the relationship between sales and customers.

7. SCD LOGIC

Dimension SCD Type Changed attributes Justification
DIM_Date 0 - Dates immutable
DIM_Supplier 0 - Supplier identity stable
DIM_Product 1 (overwrite) ProductName, ListPrice, Colour, Material Corrections tolerated; no historical query requires old values
DIM_Customer 2 (expire + insert) PostalCode, StreetAddress, City, FederalState, PlzRegion, PlzZone Relocation may change PLZ and street address. Historical order assignment matters for analytics.
The following attributes are used to track changes in customer address:
Column Type Description
ValidFrom DATE Row start date (CustomerSince for first load; ETL date on change)
ValidTo DATE Row end date (NULL = active)
IsCurrent INTEGER 1 = active; 0 = historical
